# Customservice 项目分析、原型方案与开源工具调研

> 日期：2026-08-17
> 分析范围：产品文档、前后端实现、基础设施、阶段验收记录、现有两版静态原型、GitHub 开源设计工具与 MCP。

## 1. 结论先行

这个项目不是“做一个 AI 聊天客服”，而是在做一套面向出海硬件厂商的**设备上下文约束型售后诊断系统**。真正的差异化来自四件事：

1. 扫码后确定型号、硬件、固件和地区，先限定知识适用范围；
2. 高频故障由已审核的确定性状态机推进，而不是让模型自由编步骤；
3. 安全风险、证据不足、保修退款等场景强制降级到人工；
4. 人工结案结果进入可审核的知识、流程和产品质量队列，不直接污染知识库或模型。

工程实现已经明显超过概念阶段：模块化 Spring Boot 后端、React 管理台与用户端、Flyway 数据模型、知识处理、混合检索、诊断流程版本、人工交接、运营评测和双语已经存在。当前最大的风险不是“功能还没写”，而是**真实试点链路尚未被外部依赖和真实用户验证**。

因此，新原型不应该继续扩充静态后台页面，而应成为一条可连续演示、可拿去访谈的试点闭环：

```text
扫码识别 → 受控诊断 → 安全停止 → 人工接管 → 结案回流
```

## 2. 产品与用户判断

### 2.1 目标客户

- 海外年销售额约 1–5 亿元人民币的硬件厂商；
- 首选 Android 机顶盒、投影仪、智能电视、智能家居等售后知识复杂、SKU/固件差异明显的品类；
- 首个试点应限制在一家客户、一个产品系列、少量高频故障，不应先追求全行业平台化。

### 2.2 两类核心用户

| 用户 | 核心任务 | 体验重点 |
| --- | --- | --- |
| 终端用户 | 扫码后快速、安全地排查设备故障 | 少输入、明确步骤、能看到设备识别结果、知道何时停止 |
| 运营/客服/知识专家 | 管理产品知识、审核流程、处理人工工单、发现质量问题 | 高密度、可追溯、版本清晰、责任边界明确 |

### 2.3 首个可验证价值

第一阶段不要承诺“替代客服团队”，而应证明：

- 同一问题能否根据型号/固件/地区给出不同且正确的答案；
- 高频问题是否能按流程稳定推进；
- 高风险操作是否 100% 被拦截；
- 转人工后用户是否不必重复描述；
- 结案数据能否暴露知识缺口、流程缺口或产品质量信号。

## 3. 当前工程现状

### 3.1 技术结构

| 层 | 当前实现 |
| --- | --- |
| 用户端 | React + TypeScript 扫码支持页，支持 SSE 流式回答、步骤卡、图片附件、产品切换、反馈与转人工 |
| 管理端 | 产品/变体/固件、二维码、文档、检索、诊断流程、人工转接、模型配置、运营分析共 8 个页面 |
| 后端 | Java 21 + Spring Boot 3.3.2，按 identity/product/qr/knowledge/conversation/troubleshoot/handoff/llm/analytics 模块化 |
| 数据 | PostgreSQL + Flyway，覆盖租户、产品、知识版本、会话、流程快照、工单、评测与保留策略 |
| AI 依赖 | MinIO、Qdrant、本地 OCR、Embedding/Rerank、OpenAI 兼容 LLM Provider |
| 部署 | Docker Compose 基线；外部端口默认绑定 127.0.0.1，由网关负责 TLS 与访问控制 |

### 3.2 已经形成的产品资产

- 产品主数据与二维码上下文不是附属字段，而是检索和诊断的约束条件；
- 知识修订具备上传、处理、审核、发布、弃用、归档、恢复生命周期；
- 诊断流程有定义、版本快照、节点、模拟、审核发布与恢复；
- 人工交接包包含对话、设备、步骤、风险与引用，且支持队列、认领、优先级、备注和结案；
- 运营侧已有事件、延迟、评测用例与评测运行模型；
- 生成式回答可以关闭，关闭后系统仍能进行意图、检索、状态机与交接。

### 3.3 文档与代码之间的漂移

- README 的早期目录描述仍提到 6 个后台页，但当前代码已经是 8 个页面；
- README 前部还沿用较早 Flyway 版本描述，当前迁移已经到 V25；
- 2026-07-29 的发布审计只确认当时的 37 个后端测试和 4 个前端测试，不能代表当前提交的完整状态；
- 旧审计明确没有验证真实 PostgreSQL 迁移、Compose 全依赖、浏览器 E2E、真实外部人工渠道和登录后的真实试点链路。

这意味着文档可作为产品与架构依据，但不能把旧验收记录当成当前生产就绪证明。

## 4. 项目优势与关键风险

### 4.1 优势

1. **定位正确**：避开“上传 PDF 聊天机器人”的同质化，聚焦设备上下文和故障状态机。
2. **安全边界明确**：LLM 不是流程控制器，安全停止和人工降级是强规则。
3. **领域模型较完整**：知识、流程、会话、交接和评测之间已经能形成闭环。
4. **可私有化基线存在**：OCR、向量、重排可本地运行，只有受控内容进入外部模型。
5. **UI 语言已经形成**：teal=AI、orange=人工、red=安全停止，适合继续固化为产品设计系统。

### 4.2 关键风险

| 风险 | 当前表现 | 下一步验证 |
| --- | --- | --- |
| 知识冷启动 | 文档结构和质量依赖试点客户 | 用一个真实产品系列完成数据审计和知识适用性标注 |
| 外部 AI 依赖 | 本地单测不能证明 OCR/Qdrant/Embedding/LLM 组合链路 | Compose + 真实样本文档 + 故障注入 |
| 人工渠道 | 目前以内部队列为主 | 选定 Chatwoot/WhatsApp/邮件之一，验证投递、幂等、回写 |
| 指标真实性 | 原型与分析页数据为演示值 | 在试点前定义埋点口径，首周人工抽检全部高风险会话 |
| 多语言质量 | 系统双语不等于专业术语正确 | 建立产品术语表、禁止翻译项和地区政策差异 |
| 安全与责任 | 规则存在但需覆盖真实产品风险 | 与客户售后/法务共审停止条件和保修政策 |
| 复杂前端文件 | SupportPage、FlowsPage 已较大 | 后续按稳定子域拆分，避免继续把状态与交互堆在单文件 |

## 5. 新原型的定位与内容

仓库新增：`prototype/pilot-validation/`。

### 5.1 为什么不覆盖旧原型

- `ui-prototype.html` 覆盖页面较多，适合展示早期信息架构；
- `ui-prototype-2026.html` 已形成 Precision Instrument Console 视觉方向，适合展示设计系统；
- 新原型解决不同问题：它用于让试点客户、售后专家和研发在 5 分钟内走完关键业务闭环。

### 5.2 可演示路径

1. 扫码识别 X100 / rev.B / FW 2.1.0 / EU；
2. 选择 Wi-Fi 无法连接；
3. 完成网络可见性与重启复测；
4. 命中烧焦气味，系统强制停止继续通电；
5. 自动生成 `HAND-240817-38` 交接包；
6. 人工认领、选择结案原因并结案；
7. 运营侧新增一条待审核产品质量信号。

### 5.3 原型技术约束

- 纯 HTML/CSS/JavaScript，无外部依赖；
- 使用真实业务术语和代表性数据，不调用后端；
- 中英切换、关键状态转换、移动端布局和 `localStorage` 演示进度可用；
- 桌面和 390px 移动端已通过浏览器检查；完整闭环可点击走通。

## 6. GitHub 开源原型工具与 MCP 调研

以下数据为 2026-08-17 的 GitHub 快照，星标只是成熟度辅助信号，不代表适配度。

| 工具 | 类型 | 适合做什么 | 当前判断 |
| --- | --- | --- | --- |
| [OpenDesign](https://github.com/manalkaff/opendesign) | Codex/Claude/Cursor 设计技能包，MIT | 读取现有代码设计系统，输出 repo-native HTML/React 可交互原型 | **最适合本项目当前阶段**；轻量、贴近代码，但不是 MCP，且项目较新 |
| [Penpot + 官方 MCP](https://github.com/penpot/penpot/tree/develop/mcp) | 开源设计平台 + 官方双向 MCP，MPL-2.0 | 团队共同维护设计源文件，AI 创建/读取/修改画布 | **最适合长期开放设计源**；能力完整，但部署与连接链路更重 |
| [Figma Console MCP](https://github.com/southleft/figma-console-mcp) | 第三方双向 Figma MCP，MIT | 读取设计系统、创建画布、调试与 token 同步 | 团队已用 Figma 时值得评估；第三方桥接权限面较大，需要安全审查 |
| [Figwright](https://github.com/awdr74100/figwright) | 本地双向 Figma MCP，MIT | 不依赖 Dev Mode，通过本地插件读写当前 Figma 文件 | 更轻的 Figma 路线，适合个人/小团队试验；仍较新 |
| [Excalidraw MCP](https://github.com/excalidraw/excalidraw-mcp) | 官方 MCP App / 白板 | 用户旅程、架构、服务蓝图、低保真讨论 | 非常适合线框和流程共创，不适合承担高保真产品原型 |
| [TypeUI](https://github.com/bergside/typeui) | 设计指导资源 + MCP | 给编码代理提供设计系统、布局变体和 UI 指导 | 适合提升代码生成质量，不是独立原型画布；需确认许可证边界 |
| [Framesmith](https://github.com/vicmaster/framesmith) | HTML/CSS 场景图 MCP，MIT | 代理在可视画布中生成和评分界面 | 思路契合，但仓库很新、社区和生产证据弱，暂不作为主链路 |

### 6.1 推荐组合

当前阶段建议采用：

```text
OpenDesign（代码库内高保真交互原型）
    + Excalidraw MCP（旅程/流程/共创草图，可选）
    + Penpot MCP（进入多人设计协作后再引入）
```

如果团队已经把 Figma 作为设计源，则用 Figwright 或 Figma Console MCP 替换 Penpot；不要同时维护 Penpot、Figma 和 HTML 三套源。

## 7. OpenDesign 能不能用

结论：**能用，而且与当前仓库很匹配；但应把它理解为设计工作流技能包，不是 MCP 服务。**

本次做了以下实查：

- 仓库为 MIT 许可证，包含 Codex 插件清单；
- 提供 `opendesign`、`create-design-system`、`wireframe`、`interactive-prototype`、`make-tweakable` 等 10 个技能；
- `interactive-prototype` 明确要求真实状态转换、表单验证、加载/空状态、移动端 44px 点击目标和 `localStorage`；
- 浅克隆后执行仓库自带 `validate-skills.sh`，全部技能结构验证通过；
- 最新正式 release 为 v0.3.1（2026-05-05）；项目在 2026 年才创建，仍属于快速演化期。

### 7.1 适配本项目的优点

- 能先读 `tailwind.config.js`、CSS 令牌和现有页面，再提取设计系统；
- 输出仍在 Git 仓库中，研发可以直接审查和迁移；
- 适合把现有 `Precision Instrument Console` 固化为可复用设计系统；
- 可交互原型强调状态而非静态截图，与诊断状态机产品非常契合。

### 7.2 使用时的注意点

- 它的默认流程偏重：新任务会要求较完整 intake，并依赖验证代理；小改动需控制流程成本；
- HTML 原型不是最终产品代码，迁移到 React 时仍需重新对齐真实 API、i18n、a11y 和组件契约；
- 技能本身会读取仓库并生成文件，安装前应审查版本，锁定 commit/tag，不要无审查地跟随 `main`；
- 当前 Codex 会话中 OpenDesign 尚未安装，因此本次原型按其公开规范进行结构验证，但没有声称调用了已安装的 OpenDesign 插件。

### 7.3 建议的落地方式

1. 在 Codex App 的 Plugins 中安装 OpenDesign，并锁定一个经过审查的版本；
2. 从当前前端的 Tailwind、全局 CSS、`ui.tsx` 与 `UI方案.md` 生成项目设计系统；
3. 把新原型迁入 OpenDesign 的 `opendesign/mockups/` 工作流；
4. 每次原型只验证一条任务链，不按后台菜单数量堆页面；
5. 评审通过后，再把明确状态和组件映射回 React 实现。

## 8. 建议的下一步

### P0：用原型做一次共创评审

邀请产品、售后专家、客服和研发各 1 人，走完整演示并回答：

- 设备上下文是否足够？
- 哪些安全词必须立即停止？
- 人工接手前还缺哪些字段？
- 结案原因如何分类才有运营价值？
- 哪个指标能决定是否扩大试点？

### P1：确定真实试点数据与渠道

- 锁定一个产品系列、两个高频故障、一个高风险故障；
- 收集说明书、错误码、固件差异、保修政策和 50–100 条历史工单；
- 选定首个人工渠道，不要同时接 Chatwoot、WhatsApp、邮件和 CRM；
- 建立术语表、停止条件和知识适用性字段。

### P2：做一次全链路技术验收

- 当前提交重新跑后端测试、前端测试、lint 和生产构建；
- 用真实 PostgreSQL 执行全部 Flyway 迁移；
- 启动 Compose 并验证 MinIO/Qdrant/OCR/Embedding/Rerank；
- 使用真实样本文档和图片验证处理、检索、诊断和交接；
- 增加浏览器 E2E 覆盖扫码 → 诊断 → 转人工的黄金路径。

### P3：把原型状态映射到生产 UI

优先迁移：

1. 用户侧设备识别确认；
2. 诊断步骤与状态轨的完成/当前/风险状态；
3. 安全停止与不可变交接包说明；
4. 人工工作台的系统摘要、时间线和结案原因；
5. 待审核知识/流程/产品信号队列。

# 海外硬件 AI 智能客服 MVP 全局开发计划

**版本：** v1.1  
**日期：** 2026-07-28  
**状态：** 已确认，待按阶段实施  
**适用目录：** `D:\CRRC\aicoding\customservice`


## 1. 现状与目标

当前代码已完成 Java/Spring Boot 基础工程、JWT/RBAC、产品和二维码基础接口、文件上传、PDF/DOCX/OCR 解析、知识修订、持久化任务、Embedding/Qdrant 初步索引及检索接口。（本地环境配置的jdk和maven位置位于D:\CRRC\jdk21和D:\dev-tools\apache-maven-3.9.16-bin\apache-maven-3.9.16
）

这些能力属于 MVP 的领域和知识底座，还不是可交付的 MVP。扫码用户端、完整知识审核后台、分块与混合检索、LLM 编排、受控诊断、人工交接、运营统计、评测体系及端到端安全验收仍需完成。

MVP 最终需要形成以下业务闭环：

```text
管理员配置产品
→ 上传并审核知识
→ 用户扫码识别设备
→ 用户进行图文对话
→ 系统限定产品范围检索
→ FAQ 回答或进入受控诊断
→ 高风险、无证据或连续失败时转人工
→ 人工处理结果回流为知识候选
→ 管理员查看统计并运行回归评测
```

MVP 完成必须满足：

- 用户不会检索到其他租户、型号、地区或未发布知识。
- 所有事实回答均带知识来源和版本。
- 无证据时拒绝编造；知识冲突时追问或转人工。
- 高风险问题停止自助操作并升级人工。
- 诊断分支由服务端状态机决定，LLM 不得自由修改。
- 人工交接包包含产品、会话、附件、错误码和已尝试步骤。
- 知识、提示词、模型或检索策略变更后可重复运行评测集。

## 2. 分阶段实施计划

### 阶段 0：工程基线与现有代码加固

先修正现有底座，避免在不稳定结构上继续增加功能。

实施内容：

- 增加 Maven Wrapper，固定 Maven 3.9+，统一使用 JDK 21。
- 建立 `dev/test/prod` 配置，并在启动时拒绝默认密码和弱密钥。
- 为 PostgreSQL、MinIO、OCR、Embedding、Rerank 和 Qdrant 配置连接、超时及健康检查。
- 调整 Worker 事务边界：领取任务、外部调用、结果回写分别使用短事务。
- 使用数据库锁或原子更新领取任务，防止并发 Worker 重复执行。
- 统一错误码、请求 ID、任务 ID 和结构化日志；禁止记录令牌、密钥、附件正文和敏感联系方式。
- 补齐租户、知识版本、语言、发布状态等检索强过滤。
- 建立后端单元测试、Repository 测试及外部 Adapter 契约测试。
- 清理前端占位状态，使页面真实反映现有能力。

验收门槛：

- 后端在 JDK 21 环境完成 `mvn test`。
- 前端完成生产构建。
- OCR、Embedding、Qdrant 或 MinIO 不可用时任务失败可追踪、可重试。
- 并发 Worker 不会重复处理同一任务。

### 阶段 1：产品与知识运营闭环

实施内容：

- 补齐产品系列、型号、硬件版本、固件范围、地区变体和型号别名。
- 二维码支持查询、撤销、失效、批次和可选序列号。
- 知识状态统一为：
  `UPLOADED → PARSING → DRAFT → REVIEW → APPROVED → PUBLISHED → DEPRECATED → ARCHIVED`。
- 原文件、解析文本、知识修订和索引版本分别保存；已发布版本不可原地覆盖。
- PDF、DOCX 和图片解析后生成可人工检查的文本预览。
- 实现知识分块，保存块序号、页码、标题层级、来源和适用范围。
- 发布时生成新索引版本；下架和回滚时同步更新 Qdrant。
- 实现关键词召回、向量召回、合并去重和本地 Rerank。
- 检索必须先按租户、型号、硬件/固件、地区、语言、有效期和发布状态过滤。
- 管理后台完成登录、产品、二维码、上传、解析状态、文本预览、审核、发布、回滚和检索验证页面。

验收门槛：

- PDF、DOCX、PNG 和 JPEG 均能完成上传、解析、审核、发布及检索。
- 相似型号、错误地区、过期固件和未发布知识不能被召回。
- 检索结果返回文档标题、页码、修订版本、知识块和适用范围。
- 知识下架后，新请求立即停止使用对应版本。

### 阶段 2：扫码用户端与会话基础

实施内容：

- React 应用通过路由区分 `/admin` 管理端和 `/support/{qrToken}` 用户端。
- 扫码后由服务端解析产品上下文，不信任前端提交的租户或型号。
- 创建匿名会话，记录语言、地区、产品、硬件/固件和原始扫码上下文。
- 支持文本消息、错误码和图片附件。
- 用户附件保存至私有 MinIO；图片仅用于 OCR、产品标签和错误码辅助。
- 支持语言选择、网络重试、终止回答及已解决/未解决反馈。
- 用户修改型号时结束当前诊断上下文并建立新的产品上下文版本。

主要实体：

- `Conversation`
- `ConversationProductContext`
- `Message`
- `MessageAttachment`
- `ConversationFeedback`

验收门槛：

- 有效二维码可建立限定产品的匿名会话。
- 失效、撤销及下架产品二维码有明确降级提示。
- 图片上传失败不会丢失文字消息。
- 产品范围不能通过客户端请求参数越权修改。

### 阶段 3：LLM Provider 与有依据问答

实施内容：

- 实现 OpenAI 兼容 Provider Adapter，支持 `baseUrl`、模型名、API Key、超时和启停。
- API Key 服务端加密保存，响应和日志中不得返回明文。
- 意图使用受控枚举：咨询、安装、故障、错误码、保修、投诉、安全风险、人工请求和无关内容。
- 安全规则和人工请求先由确定性规则处理，再进入模型分类。
- 建立完整 RAG 链路：产品强过滤、混合召回、Rerank、证据阈值、生成和引用校验。
- 模型只能根据检索证据回答，不允许自行创造维修步骤。
- 回答通过 SSE 流式返回，并保存模型、耗时、Token、引用块和知识版本。
- 模型、Embedding 或 Rerank 不可用时降级到已发布 FAQ 或人工入口。

验收门槛：

- 每条事实回答至少关联一个有效知识块。
- 无答案、冲突知识和错误型号问题能正确拒答或追问。
- 提示词注入不能改变租户、产品范围和安全规则。
- 任意回答均可追溯到模型配置、检索结果和知识版本。

### 阶段 4：受控诊断流程

实施内容：

- 建立 `TroubleshootFlow`、不可变流程版本、节点和分支。
- 节点类型固定为问题、操作、判断、人工升级和结束。
- 每个节点包含适用范围、用户提示、预期输入、来源知识、风险级别和停止条件。
- LLM 只负责将用户自然语言映射为 `YES/NO/UNKNOWN` 等受控结果。
- 服务端状态机决定下一节点；模型不能跳过节点或修改分支。
- 连续两次失败、安全风险、用户拒绝操作或结果不明确时进入人工升级判断。
- 管理后台提供表单式流程编辑器和模拟器；MVP 不建设复杂拖拽画布。

验收门槛：

- 实现 3–5 个高频、低风险诊断流程。
- 成功、失败、未知、拒绝操作和安全停止分支均有自动化测试。
- 用户自由表达不能绕过安全节点。
- 进行中的会话固定使用已开始时的流程版本。

### 阶段 5：人工交接闭环

MVP 默认采用“内部交接队列 + SMTP 邮件通知”，后续通过 Adapter 接入 WhatsApp 或客户工单系统。

实施内容：

- 建立统一 `HandoffRequest` 及状态机。
- 自动生成交接包：产品上下文、问题摘要、原始会话、附件、错误码、引用知识、已尝试步骤、转人工原因和联系方式授权。
- 系统和用户均可发起转人工，并使用幂等键防止重复工单。
- SMTP 失败进入可重试任务，不重复创建交接记录。
- 客服通过管理后台领取、更新和关闭请求。
- 关闭结果固定为：已解决、待配件、保修处理、用户放弃、重复问题和产品缺陷。
- 人工解决方案只能生成知识草稿，不能自动发布。

验收门槛：

- 人工无需重新询问型号和已尝试步骤。
- 邮件失败可重试且不会生成重复工单。
- 用户可看到请求编号和预计响应方式。
- 人工结果可转换为待审核知识候选。

### 阶段 6：运营统计与质量评测

实施内容：

- 记录扫码、会话、意图、检索、回答、诊断、反馈、转人工及模型失败事件。
- 统计会话数、解决率、转人工率、无答案率、差评回答、知识使用量、响应耗时和图片上传成功率。
- 建立 `EvaluationCase`、评测批次、评测结果和切片指标。
- 初始评测集默认包含：
  - 不少于 50 条有标准答案的问题；
  - 不少于 10 条无答案或相似型号反例；
  - 不少于 10 条安全风险和提示词注入样例；
  - 每个诊断流程的全部主要分支。
- 支持按型号、地区、语言、意图和风险等级查看评测结果。
- 知识、模型、提示词和检索参数变更前后使用同一评测集回归。

验收门槛：

- 管理员能定位一次差回答属于知识缺失、检索错误、生成错误还是流程错误。
- 高风险切片不得出现安全拦截退化。
- 评测结果保留版本，可比较两次发布前后的变化。

### 阶段 7：安全、部署与 MVP 发布验收

实施内容：

- 文件头校验、扩展名白名单、文件大小限制和恶意文件扫描接口。
- 联系方式与附件保留期、删除请求及日志脱敏。
- 登录、二维码解析、消息发送、模型调用和文件上传限流。
- 增加请求 ID、会话 ID、任务 ID、外部服务耗时和失败指标。
- 固定容器镜像版本，将业务后端和前端纳入 Compose。
- 补齐 PostgreSQL、MinIO 和 Qdrant 的备份恢复说明。
- 建立一键启动、健康检查、管理员初始化和演示数据脚本。
- 完成真实浏览器和端到端验收。

最终验收场景：

1. 管理员创建产品和二维码。
2. 上传 PDF、DOCX 和产品标签图片。
3. 审核发布知识并验证限定检索。
4. 用户扫码进入正确产品。
5. 完成一条 FAQ 问答。
6. 完成一条正常诊断流程。
7. 触发一条安全停止流程。
8. 无答案时正确转人工。
9. 人工关闭请求并生成知识候选。
10. 管理员查看统计并运行回归评测。
11. 模型、OCR、Qdrant 或人工渠道故障时系统正确降级。
12. 全链路不存在跨租户、跨型号或未发布知识泄漏。

## 3. 固定技术与产品决策

- 后端保持模块化 Spring Boot 单体，MVP 阶段不拆微服务。
- 前端保持一个 React 工程，通过路由区分管理端和用户端。
- 单客户独立实例运行，代码和表结构仍保留 `tenant_id`。
- PostgreSQL 保存业务数据，MinIO 保存原文件和附件，Qdrant 保存已发布知识向量。
- 使用本地 BGE-M3 Embedding 与 Rerank；外部 LLM 通过 OpenAI 兼容接口接入。
- 英语作为主语言，简体中文作为第二演示语言；试点确定后可替换第二语言。
- 人工渠道默认使用内部队列和 SMTP 通知。
- 异步任务继续使用数据库任务表，MVP 不引入 Kafka 或 RabbitMQ。
- 用户图片仅支持 OCR、标签和错误码辅助，不做硬件故障自动判断。
- 不实现自动退款、自动换货、远程控制、语音客服和完全离线大模型。

## 4. 开发执行规则

- 严格按阶段顺序实施，不跨阶段堆叠功能。
- 每个阶段先更新实施清单，再开发数据库迁移、后端、前端和测试。
- 所有实体和关键业务类保留职责注释。
- 状态转换、外部调用、拒绝决策和重试必须记录结构化日志。
- 日志不得记录令牌、密码、API Key、附件正文或敏感联系方式。
- 每阶段完成后执行后端测试、前端构建、格式检查和对应的手工验收场景。
- 静态检查不能替代真实编译、集成测试或真实浏览器验收。
- 保留用户已有未提交修改，只操作当前阶段相关文件。
- 每阶段单独汇报实现结果、验证结论和未覆盖边界。
- Git 提交仅在用户明确要求“提交”后执行。

## 5. 实施顺序

下一步从“阶段 0：工程基线与现有代码加固”开始。阶段 0 验收通过后，现有知识代码才能作为可靠的 MVP 第一阶段底座；随后依次推进阶段 1 至阶段 7，直至完成全部最终验收场景。
